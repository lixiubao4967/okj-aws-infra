# 数字货币交易所 AWS 安全体系

> 来源：AWS 面向交易所客户的安全分享会（2025）。本文整理自分享会幻灯片 + 现场笔记。
> 参考资料：Top Crypto Hacks — https://de.fi/rekt-database

交易所安全的本质：**让「动钱」这件事变得极慢、极难、且处处留痕，同时让看盘交易保持极快。** 下文的攻击链和防护矩阵，都是这句话在不同层面的展开。

---

## 一、攻击链分析（7 阶段）

攻击者（尤其国家级 APT）对交易所的攻击不是一次性行为，而是一条多阶段、长周期的杀伤链：

| 阶段 | 名称 | 攻击者动作 |
|------|------|-----------|
| 1 | **嗅探**（目标情报收集） | 扫描公开资源，收集目标资料：端口、WHOIS、域名、对象存储、代码、应用页面 |
| 2 | **自动化**（漏洞发现研究） | 自动化攻击，寻找 ROI 最高路径。常见入口：远程访问服务（SSH / MySQL / RDP / Oracle）、公开 S3 存储桶、DNS 污染/劫持、SQL 注入、0day 漏洞、DDoS、**内部人员勾结**、API 密钥泄露 |
| 3 | **入侵**（初始访问获取） | 获得控制权后延迟攻击：布置恶意软件/勒索软件/间谍软件，设置定时器（前端劫持攻击）等待时机；或立刻发起 DDoS、启动 EC2 挖矿 |
| 4 | **探索**（权限提升与横向移动） | 发现高价值系统，探索 EC2、IAM key 权限并尝试提权，探索 VPC 边界，从 S3 获取敏感数据 |
| 5 | **注入**（安装后门） | 复制/创建 IAM 与数据库、EC2 Admin 用户，取消备份计划，修改数据库，移动 S3 数据，入侵其他计算资源，**保证对被入侵系统的持续访问** |
| 6 | **渗透**（渗透演进趋势） | 多阶段、长周期准备；技术与社会工程结合；从用户侧一路打到平台基础设施 |
| 7 | **攻击**（最终变现） | 热钱包密钥窃取、冷钱包签名欺骗、智能合约漏洞利用、模拟用户转移资产 |

**要点**：攻击面正从「技术」转向「人和供应链」（阶段 6 的社会工程趋势）。技术栈每硬一层，攻击就往软的地方挪一层。

## 二、防护成熟度矩阵（客户场景 × 四阶段）

分享会给出的核心模型：把安全建设按 **客户场景（13 类）** 拆分，每类按四个成熟度阶段递进落地。

四个阶段的含义：

| 阶段 | 名称 | 定位 |
|------|------|------|
| 一阶段 | **Quick Win 快速制胜** | 立刻能做、见效快的基础动作 |
| 二阶段 | **Fundamental 基线配置** | 建立标准化基线 |
| 三阶段 | **Efficient 持续高效** | 流程化、自动化、可持续 |
| 四阶段 | **Optimized 日趋完善** | 中心化、平台化、持续优化 |

## 三、现场笔记补充（重点讲解）

幻灯片之外，讲师现场强调的要点：

### 域名防护（对应「基础设施防护」）

| 要点 | 说明 |
|------|------|
| S3 域名冒名 | 攻击者可能借用 S3 的域名冒名发内容；**一旦相似域名被抢注，你自己就创建不出来了**，所以要提前占位 |
| 相似域名注册 | 把跟自己极其相似的域名**全部注册下来**——成本很大，但这是最有效的防护手段 |
| 极其相似的域名 | 只能靠举报，没有其他技术手段能阻止别人注册；**若该相似域名托管在 AWS 上，可请 AWS 的技术人员介入处理** |
| DNSSEC | 应对域名劫持 |
| 二级域名白名单 | 乱序/非白名单域名统一转向 www 主页 |

### 统一 Base Image 的风险

- 统一 EC2 Base AMI / Docker Base Image 是好事，但要防范 **base image 被替换/污染**（供应链攻击）——所以三阶段要求「基础镜像自动构建」、四阶段「源代码自动扫描敏感信息」，正是为了让镜像来源可控、可验证。

### 网络隔离（对应「AWS 网络层防护」）

- **VPC-Peering 最好禁止**（点对点互联会扩大爆炸半径）。
- 入站流量设计中**不应出现 `0.0.0.0/0`** 这类全开放规则。
- 用 **Transit Gateway 集中管理路由表**，替代散乱的 Peering。

### 数据安全（对应「数据安全防护」）

- **跨账号备份 KYC 等重要数据**（核心敏感数据不与生产同账号）。
- **数据库密码放入另一个账号**里保管（隔离凭证与数据）。
- **流量镜像导入一个独立的安全账号**，做异常检测与留存。

### 应用安全（对应「应用层安全防护」）

- WAF + DDoS 防护为基础。
- **WAF Pipeline 托管到代码仓库**——所有 WAF 规则配置代码化沉淀，可审计、可回溯。
- ⚠️ **待确认**：现场提到「DynamoDB 的 TTL 进行冷冻」，笔记记录者当时未完全理解，含义待向讲师核实。（推测方向：利用 DynamoDB TTL 做数据的自动过期/归档，或对疑似恶意会话/令牌做时效控制——需确认。）

### 数据库

- 用户名密码统一放入 **Secrets Manager**，不硬编码。

### 自动化与运维

- 脚本化、基础设施自动化、**运维代码化（Operation as Code）**——所有变更走代码、可审计、交叉批复。

### 监控

- **必须有监控大屏**，用于评估系统整体健康程度、故障时快速定位（对应「故障响应」一阶段）。

## 四、与本团队现状的对应

分享会矩阵里的很多阶段，本团队已在 `okj-cdk-exchange` / `okj-argo-manifests` 中落地：

| 矩阵项 | 本团队对应实践 |
|--------|--------------|
| AWS 多账号管理 · 去掉 IAM User / 用 Role 登录 | CDK 规则：凭证不写入任何项目文件、用临时角色凭证 |
| 数据库 · Secrets Manager | secret-stack（部署时踩过 `cdk import` 坑） |
| 变更操作代码化 · 可审计交叉批复 | ArgoCD 三层 GitOps（base / overlays / argocd），变更走 Git 审批留痕 |
| 基础设施代码化 IaC | okj-cdk-exchange（CDK Go 4 层架构） |
| 统一 Base Image | ops-kit CI Image |
